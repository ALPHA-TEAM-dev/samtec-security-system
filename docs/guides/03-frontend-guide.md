# Frontend guide

For Samuel, who builds the dashboard. Francis should read "How a page loads data", because that is where the frontend and backend meet.

## What the dashboard is

A React single-page app. The browser downloads it once, and after that every screen gets its data from the API through the contract. It never talks to the database.

## Running it

| Command (from the repository root) | What you get |
|---|---|
| `pnpm dev:web` | Dashboard with **mock data**. No API or database needed. Use this most of the time. |
| `pnpm dev` | Dashboard and API together, with real data. Needs `pnpm db:start` in another terminal. |
| `pnpm dev:web:live` | Dashboard only, calling an API that is already running |

The top bar always shows **Mock data** or **Live API**, so nobody mistakes pretend data for real data.

## React in five ideas

1. **Components** are functions that return what to show: `function EmployeesPage() { return <div>…</div>; }`.
2. **JSX** is the HTML-like syntax inside components. Use `className` instead of `class`.
3. **Props** are a component's inputs: `<EmployeeStatusBadge status="ACTIVE" />`.
4. **State** (`useState`) is data a component remembers, such as the text in a search box. Changing state re-draws the component.
5. **Hooks** are functions starting with `use`. They add abilities to a component: `useState` for memory, `$api.useQuery` for loading data.

## How a page loads data

Open `src/pages/system-status-page.tsx`. The important line is:

```tsx
const health = $api.useQuery('get', '/health');
```

- `'get'` and `'/health'` must exist in the contract, or TypeScript shows a red error.
- `health.data` has exactly the contract's `HealthResponse` shape.
- `health.isPending` is true while the first load is running.
- `health.error` holds the error body when the request fails.
- `health.refetch()` loads it again.

Every page that loads data must show **three states besides the data itself:**

| State | What the user sees |
|---|---|
| Loading | Skeletons (grey placeholder shapes) |
| Error | A clear message, the trace ID, and a "Try again" button |
| Empty | A sentence such as "No employees match these filters." |

`src/pages/employees-page.tsx` is the full reference: search, a status filter and cursor pagination. Copy its structure for new list pages.

### Cursor pagination in plain words

The API returns one page and a `nextCursor`, a bookmark for the next page. The employees page keeps a list of the bookmarks it has used:

- **Next:** add `nextCursor` to the list and load the page for it.
- **Previous:** remove the last bookmark and load the page before.
- **Search or filter changes:** start again from the first page.

## Adding a page, step by step

Example: the **Sites** page (Phase 1). The endpoint `GET /sites` is already in the contract, and the mock API already answers it.

### 1. Create the page

```tsx
// src/pages/sites-page.tsx
import { Card } from '@/components/ui/card';
import { Skeleton } from '@/components/ui/skeleton';
import {
  Table,
  TableBody,
  TableCell,
  TableHead,
  TableHeader,
  TableRow,
} from '@/components/ui/table';
import { $api } from '@/lib/api';
import { describeApiError } from '@/lib/problem';

export function SitesPage() {
  const sites = $api.useQuery('get', '/sites', { params: { query: { limit: 25 } } });

  if (sites.isPending) {
    return <Skeleton className="h-40 w-full" />;
  }
  if (sites.isError) {
    return <p role="alert">{describeApiError(sites.error).message}</p>;
  }
  if (sites.data.items.length === 0) {
    return <p className="text-muted-foreground">No sites yet.</p>;
  }

  return (
    <Card className="overflow-hidden py-0">
      <Table>
        <TableHeader>
          <TableRow>
            <TableHead>Code</TableHead>
            <TableHead>Name</TableHead>
            <TableHead>City</TableHead>
            <TableHead>Guards on post</TableHead>
          </TableRow>
        </TableHeader>
        <TableBody>
          {sites.data.items.map((site) => (
            <TableRow key={site.id}>
              <TableCell className="font-mono text-xs">{site.code}</TableCell>
              <TableCell>{site.name}</TableCell>
              <TableCell>{site.city}</TableCell>
              <TableCell className="tabular-nums">{site.activeGuardCount}</TableCell>
            </TableRow>
          ))}
        </TableBody>
      </Table>
    </Card>
  );
}
```

### 2. Give it a web address

In `src/app/router.tsx`, add it to `children`:

```tsx
{ path: 'sites', element: <SitesPage /> },
```

### 3. Switch on its link

In `src/components/layout/nav-items.ts`, set `available: true` on the Sites item.

### 4. Test it

```tsx
// src/pages/sites-page.test.tsx
import { screen } from '@testing-library/react';
import { describe, expect, it } from 'vitest';
import { renderWithProviders } from '@/test/render';
import { SitesPage } from './sites-page';

describe('SitesPage', () => {
  it('lists sites from the API', async () => {
    renderWithProviders(<SitesPage />);

    expect(await screen.findByText('Ridge Towers Office Complex')).toBeInTheDocument();
  });
});
```


## The mock API (MSW)

The mock API lives in `src/mocks/`:

- `handlers.ts` answers requests the way the real API will, including errors.
- `data/` holds fictional employees and sites.
- In mock mode, `main.tsx` starts it inside the browser. In tests, `src/test/setup.ts` starts it inside Node.js.

**Rules:**

- Use contract types for every response body, so TypeScript catches mistakes.
- When the contract changes, update the handlers in the same pull request.
- Mock data is always fictional. Never copy real people into it.

**Simulating an error in a test:**

```tsx
server.use(
  http.get(`${env.apiBaseUrl}/employees`, () =>
    HttpResponse.json(
      { type: 'about:blank', title: 'Internal Server Error', status: 500, detail: 'The database is not available.', traceId: 'test' },
      { status: 500 },
    ),
  ),
);
```

`src/pages/employees-page.test.tsx` shows this in a complete test.

## Sending data (from Phase 1)

Creating or changing data uses `useMutation`. After it succeeds, tell React Query that the list is out of date so it reloads:

```tsx
import { useQueryClient } from '@tanstack/react-query';
import { $api } from '@/lib/api';

const queryClient = useQueryClient();
const createEmployee = $api.useMutation('post', '/employees', {
  onSuccess: () => queryClient.invalidateQueries({ queryKey: ['get', '/employees'] }),
});

// Later, for example in a form's submit handler:
createEmployee.mutate({ body: newEmployeeDetails });
```

Forms will use react-hook-form with Zod schemas. They are added, and logged as a stack decision, in Phase 1.

## UI components (shadcn/ui)

The components in `src/components/ui/` are copied into our code, so you can read and change them. Use them instead of building buttons, tables or dialogs from scratch.

**Adding a component** (run inside `apps/web`):

```bash
cd apps/web
pnpm dlx shadcn@latest add dialog
```

Then import it: `import { Dialog } from '@/components/ui/dialog';`.

Biome does not lint or format `src/components/ui/`, so components can be updated later with the shadcn CLI without style conflicts. Your own components elsewhere follow Biome's rules as usual.

If pnpm refuses a new dependency because of a security rule, stop and tell Francis. Never switch the rule off.

**Styling with Tailwind** uses small class names:

| Class | Meaning |
|---|---|
| `flex items-center gap-2` | Items in a row, vertically centred, with a small gap |
| `grid gap-4 sm:grid-cols-2` | A grid with two columns on screens wider than a phone |
| `text-sm text-muted-foreground` | Small, softer text |
| `font-semibold text-2xl` | A page heading |
| `tabular-nums` | Digits line up in columns |

`cn()` (imported from `cn`) merges class names safely, for example `cn('px-3', isActive && 'font-medium')`.

## Formatting rules

Always use the helpers in `src/lib/format.ts`:

| Show | Use | Never |
|---|---|---|
| Money | `formatCedis(amountPesewas)` → `GH₵ 1,234.56` | `amount / 100`, `toFixed` |
| A calendar date | `formatDate('2026-09-15')` → `15 Sept 2026` | `new Date(...).toLocaleDateString()` |
| A timestamp | `formatDateTime(isoTimestamp)` → Ghana time | the viewer's local time zone |

## Accessibility checklist

- Every input has a `<Label htmlFor>` that matches its `id`.
- Every button has visible text or an `aria-label`.
- Decorative icons have `aria-hidden="true"`.
- Status is never shown by colour alone (the status badge includes text).
- Everything works with the keyboard alone: try Tab and Enter.

## Security rules for the dashboard

- Never put secrets in `VITE_` settings. Everything in the dashboard is public.
- From Phase 1, keep the access token in memory only; never use `localStorage` or `sessionStorage` for tokens.
- Never use `dangerouslySetInnerHTML`.
- Show only the fields a screen needs, especially Ghana Card and phone numbers.

## Testing

| Command | What runs |
|---|---|
| `pnpm --filter @samtec/web test` | All dashboard tests |
| `pnpm --filter @samtec/web test:watch` | Re-runs tests as you save |

Testing tips:

- Render pages with `renderWithProviders` from `src/test/render.tsx`.
- Use `await screen.findByText(...)` for anything that appears after loading.
- Use `userEvent` to type and click like a person.
- Find elements the way a user would: by label, by role and by visible text.

## Troubleshooting

| Problem | Fix |
|---|---|
| Red TypeScript error on `$api.useQuery('get', '/something')` | The path or parameters are not in the contract. Check `openapi.yaml`, or change the contract first. |
| The page shows "Could not reach the SAMTEC API" | You are in live mode without the API. Use `pnpm dev:web`, or start the API. |
| A test fails with "request … has no matching handler" | Add a handler to `src/mocks/handlers.ts`, or use `server.use(...)` in that test. |
| Styles look broken | Stop the dev server and start it again. Check `src/index.css` still starts with the Tailwind import. |
